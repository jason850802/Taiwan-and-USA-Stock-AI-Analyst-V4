# 2026-09-25：啟動環境時的繞路

## 發生經過

1. 我先在受限執行環境查 `Get-CimInstance Win32_Process`，得到「拒絕存取」，卻把空結果誤當作沒有殘留程序。這不是有效的程序盤點。
2. 我用 `Start-Process powershell.exe -NoExit -Command ...` 開了兩個 PowerShell 視窗。主機後來證實視窗 PID 存在，但沒有 npm／npx 子程序，3000／3001 也沒有監聽。我當時無法讀到視窗內的錯誤文字，因此**不能斷言**初次失敗是引號、工作目錄或其他特定原因。
3. 我重複輪詢埠，並嘗試透過桌面工具看視窗；該工具沒有列出原生 App，`listWindows` 也不可用。輪詢指令還兩次寫出 `foreach { ... } | Format-Table`，在 PowerShell 觸發 `An empty pipe element is not allowed.`。這些步驟沒有幫助定位啟動失敗。
4. 改用主機權限後，先查明兩個視窗無服務子程序，再用專案工作目錄及 `C:\Program Files\nodejs\npx.cmd`／`npm.cmd` 的完整路徑重開。此時 3000／3001 都有 node 監聽，兩個 `localhost` 根頁面均回 HTTP 200。
5. 把啟動流程做成 `.ps1` 後，我第一次用 Windows PowerShell 5.1 `-File` 檢查又碰到 `running scripts is disabled on this system`。先前查到的 `RemoteSigned` 是另一個 PowerShell 執行環境，不能推論 5.1 的預設。最後只在新 PowerShell 程序指定 `-ExecutionPolicy RemoteSigned`，沒有修改持久設定。

## 固定修法

- `start-dev` 指向 `scripts/start-dev.ps1`。腳本先確認能讀取主機程序，再讀 `.env` 的變數名稱；在受限環境無法確認程序時立即停止。
- 新視窗用 `powershell.exe -File` 呼叫同一支腳本的服務模式，避免再次把多層引號塞進 `-Command`。子視窗以 `Get-Command` 解析 `.cmd` 的完整路徑。
- 只在缺少服務時開視窗；已占用埠先核對程序身分，不自動殺程序。啟動後檢查兩個埠及 HTTP 回應，失敗直接提示讀視窗日誌。

這是本機開發環境的教訓，不表示 03 票的 API 對等、原來源 App 驗收或部署行為已通過。

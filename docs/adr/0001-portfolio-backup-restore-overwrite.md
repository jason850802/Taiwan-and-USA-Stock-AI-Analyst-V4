# ADR-0001: 庫存備份採「五把本體 key ＋ 覆蓋式回灌」

- 日期：2026-07-27
- 狀態：已拍板（grill-with-docs 五題五答，使用者逐題確認）
- 階段：P1 邊界決策；實作規格另走 to-spec

## 背景

全部庫存資料只活在單一瀏覽器（Edge）的 localStorage：769 筆真實交易、持股、
已實現損益、配息推算與手動調整，清瀏覽器資料／換電腦／profile 損毀即滅失，
且重建不回來（對帳單原檔救不回配息推算結果與手動修正）。App 至今沒有任何
匯出路徑——全 repo 唯一的 `new Blob` 在 xlsx 解壓（方向相反）。

## 決策

1. **分階段**：P1＝JSON 備份＋回灌（保命）；P2＝給 Excel 的 CSV 報表。
   兩者獨立驗收，P2 可永遠不做；CSV 的欄位／編碼細節等 P2 開工再 grill。
2. **備份範圍＝五把本體 key**：`portfolio_items`、`portfolio_transactions_v1`、
   `portfolio_import_log_v1`、`portfolio_realized_trades_v1`、`portfolio_snapshots_v1`。
   排除可重建者：`portfolio_close_cache_v1`（收盤價可重抓，回灌後曲線頁自動補）、
   `gemini_cache_v1|*`（當日即棄）。備份檔裡每一個位元組都是重建不回來的。
3. **回灌語意＝覆蓋式**：整包換掉，不做合併、不做部分回灌。
   依據：已實現帳本與每日快照**沒有去重鍵**，合併會把同一筆賣出的損益算兩次
   且 UI 無任何異常徵兆；「兩台電腦各記一半」的需求場景目前不存在。
4. **回灌防護網兩道**：(a) 確認框列實際筆數對照——「現有 N 持股／M 交易／K 已實現
   → 換成備份檔的 n／m／k（匯出於某日某時）」；(b) 按確認當下自動下載一份
   現況預備份再覆蓋（現況全空則跳過，不下載空檔）。
5. **「清空全部資料」不進 P1**——獨立的毀滅性功能，需要自己的防護設計，
   目前無此需求；真需要時再開票。

## 後果與約束

- 備份檔自帶 schema 版本＋匯出時間；**未知版本整包拒收、現有資料一個位元組不動**
  （沿用 txnStore 未知版本的處理慣例）。
- 覆蓋式的代價：備份之後新增的資料，回灌即捨棄——風險由預備份吸收。
- 往返鐵則（spec 必含此測試）：匯出 → 清空 → 回灌後，五把 key **逐位元組相同**。
- 禁裝新套件（專案紅線）：下載用原生 `Blob` ＋ `createObjectURL`。
- 這不是雲端同步：備份檔在使用者電腦上，換機自帶。

## 未決（留給 to-spec）

## 問題陳述

使用者定期定額買入美股碎股（實例：LITE 三批 1.2048／1.08896／0.50824，合計 2.802 股）。
儲存層與解析器早已支援小數股數、明細列顯示正確，但：

1. 庫存**群組列把 2.802 顯示成 3**（股數格式化預設 0 位小數）；已實現帳本、
   匯入缺口列、賣出視窗共四處同病。
2. 匯入對帳單時，**碎股賣出被浮點誤差誤殺**：三批加總在浮點運算下是
   2.8019999999999996，比對帳單的 2.802 少 4.4e-16，重播引擎的無容差比較誤判
   「持股不足」→ 跳出「賣出 0 股找不到買進紀錄」的幻影缺口 → 整筆賣出被略過，
   **庫存沒扣、已實現帳本沒記**——碰錢的數字錯，帳本失去對帳價值。
3. 使用者這筆被誤殺的賣出，其去重鍵可能已被記成「已匯入」，修好引擎後重匯同檔
   會被去重擋掉，需要一次性資料修復。

## 解法

容差進引擎、精度歸儲存、取整只留顯示（ADR-0004）：

- 新增**股數單位模組**（utils 層純函式模組）：`SHARE_EPS = 1e-6` 常數＋
  `fmtShares` 顯示格式化，單一出處、兩個引擎與四個顯示點共用。
- 匯入重播引擎的缺口閘門加容差：差距 > SHARE_EPS 才算真缺口；容差內視為足額賣出。
- 手動賣出引擎的滿賣判定與超賣擋板加同一容差，容差內以持有數為準（clamp）入帳。
- 四個顯示點換用 fmtShares；所有輸入欄維持精確往返，fmtShares 禁入輸入欄。
- 使用者現有資料走一次性修復 runbook（診斷 → 視情況清鍵 → 重匯 → 驗證）。

## 使用者故事

1. 作為買美股碎股的使用者，我要庫存群組列的總股數顯示真實小數（2.802 而非 3），讓我看到的持股跟券商 App 一致。
2. 作為使用者，我要對帳單裡的碎股賣出正常匯入（扣庫存、記已實現、費稅取帳單實數），不再因浮點噪音被當成「找不到買進紀錄」。
3. 作為使用者，當真的有期初缺口時（例如真缺 1.802 股的買進紀錄），我仍要看到缺口提示並能補成本——容差只吃掉噪音，不吃掉真缺口。
4. 作為使用者，我要已實現帳本的股數欄顯示碎股原值，讓帳本能與對帳單逐筆對上。
5. 作為使用者，我要賣出視窗顯示的持有股數是精確值（1.08896 而非 1.089），且「全部」鈕仍精確帶入可全賣。
6. 作為使用者，手動賣出碎股批次時，輸入與持有數差在 0.000001 股以內要視為全賣，不要留下 2e-16 股的塵埃批次，也不要被誤擋「超過持有股數」。
7. 作為使用者，我要整數持股的顯示完全不變（3 顯示「3」、12,000 顯示「12,000」），台股畫面跟以前一模一樣。
8. 作為使用者，我這次被誤殺的 LITE 賣出要有修復路徑：修好後重匯同一份對帳單能把賣出補記回去，庫存、帳本、歷史曲線三者歸一致。
9. 作為維護者，既有測試案例零修改由設計保證：容差只放寬「噪音級」邊緣，整數與精確值路徑的可觀察行為不變。

## 實作決策

### 股數單位模組（新增，utils 層）

- `SHARE_EPS = 1e-6`：常數註解必須帶依據（券商碎股最小單位 1e-5、浮點累積噪音
  ~1e-13，取兩者之間）。**單一出處**：匯入重播與手動賣出引擎一律 import，
  各自寫死數字＝違反 ADR-0004。
- `fmtShares(n)`：先 round 到 6 位小數吸噪音，再以 zh-TW locale 輸出
  （千分位、最多 6 位小數、去尾零）。對照表（即單元測試案例）：

  | 輸入 | 輸出 |
  |---|---|
  | 2.8019999999999996 | 「2.802」 |
  | 1.08896 | 「1.08896」 |
  | 0.50824 | 「0.50824」 |
  | 3 | 「3」 |
  | 12000 | 「12,000」 |
  | 0.000001 | 「0.000001」 |

### 匯入重播引擎（缺口閘門，唯一改動點）

- 現行：池子加總 `<` 賣出股數即成立缺口。改為：**`賣出股數 − 池子加總 > SHARE_EPS`
  才成立缺口**；容差內視為足額賣出，FIFO 吃整池。
- 金額守恆不靠容差：既有「末筆吃餘數」分攤保證 Σ各片費／稅／價金嚴格等於帳單總額，
  此機制**零變更**。
- 其餘全部零變更：FIFO 排序、費用取帳單實數（D-06）、塵埃批次 1e-9 過濾、
  乘先除後、缺口補值造 synthetic lot 的路徑。
- 效果：幻影缺口（差距在噪音級）不再產生；真缺口（差距 > 容差）行為與現在完全相同。

### 手動賣出引擎（滿賣／超賣容差）

- 超賣擋板：`賣出股數 > 持有股數 + SHARE_EPS` 才拋錯（訊息中的持有股數改用
  fmtShares 呈現，不再印出噪音浮點）。
- 滿賣判定：`持有股數 − 賣出股數 ≤ SHARE_EPS` 即視為全賣（批次移除、回 null）。
- **clamp**：容差內的有效賣出股數一律取持有股數（帳本記的是真實持有數，不是使用者
  手滑多打的那個值），成本基礎比例永不超過 100%。
- 費稅公式、匯率換算、SellResult 形狀、當沖判定全部零變更。

### 顯示端（四點換 fmtShares）

- 持股表**群組列**的總股數（本次截圖 bug）。
- **已實現帳本**的股數欄。
- **匯入視窗缺口列**的「賣出」欄（真缺口顯示 1.802 而不是 2 或 0）。
- **賣出視窗**的「持有 X 股」文字。
- **紅線——fmtShares 禁入輸入欄**：明細編輯格與「全部」鈕維持 `String(value)` ↔
  `parseFloat` 精確往返（千分位逗號會讓 parseFloat 把 2,802 讀成 2）。
- 不動：股票股利欄（整數語意）、所有金額欄、AI 提示詞的股數插值（原值即可）。

### 明確零變更清單

- 解析器（碎股解析已有行為鎖 Case G）。
- 流水回推引擎（賣出迴圈本有 1e-9 防護＋「賣超忽略」語意）。
- 匯入紀錄語意：維持「確認即記鍵」（拍板 2）——被略過交易的鍵照舊記錄；
  本次 LITE 的誤傷用票 04 一次性修復。
- 備份 schema（無任何資料模型欄位變更）。
- 台股股數整數防呆（拍板 4：本輪不做）。
- 資料模型 types 零變更（`shares`／`totalShares` 本來就是 number）。

## 測試決策

- **接縫**：匯入重播引擎測試檔＋賣出引擎測試檔＋股數單位模組新測試檔；
  不寫元件測試（專案慣例）。既有案例**零修改**（紅線），新增不受限。
- 手算對數紀律：期望值先手算再寫斷言。
- 匯入重播新增案例：
  - **LITE 實例（幻影缺口消滅）**：三批 1.2048／1.08896／0.50824 ＋ 賣出 2.802
    （帳單 gross／fee 取整數易手算的值）→ 缺口 0、sells 1、trades 3、lots 清空；
    Σ sharesSold 用 toBeCloseTo(2.802)；**Σ grossProceeds／sellFee／sellTax 與帳單
    總額嚴格相等**（守恆斷言）。
  - **真缺口仍要報**：池 1.0 賣 2.802 → gap sharesMissing ≈ 1.802（toBeCloseTo）、
    整筆略過（既有語意）。
  - **界線**：差距略大於容差（如 2e-6）→ 缺口成立。
  - **反向噪音**：池子比賣出多 ≤1e-9 塵埃 → 賣完後殘餘批次被既有塵埃過濾清掉。
- 賣出引擎新增案例（美股碎股批次）：
  - 精確滿賣：輸入＝持有 1.2048 → 全賣、updatedLot 為 null。
  - 容差滿賣＋clamp：輸入 1.2048005（差 5e-7）→ 全賣、trade.sharesSold ＝ 1.2048。
  - 超賣仍擋：輸入 1.2049（差 1e-4）→ 拋錯。
  - 部分賣出照舊：輸入 0.5 → 批次剩 0.7048、等比縮減。
  - 台股整數案例不動（零修改由設計保證的證明）。
- fmtShares：上表六案。
- **驗收**：收尾 `npm run gate` 全綠；UI 驗證量數字不靠肉眼（DOM 驗證群組列／帳本
  的顯示字串）；merge 帶 `Code-Review:` trailer。
- **findings 紀律**：實作中翻出的可疑行為 append 進同目錄 findings.md，不順手修。

## 資料修復（使用者實機，票 04）

引擎與顯示修好合併後，使用者依 runbook 操作：先下載備份 → Console 診斷 snippet
判斷 LITE 賣出鍵是否已記入匯入紀錄 → 已記則清鍵 → 重匯同一份對帳單 → 驗證
庫存 LITE 批次歸零、帳本出現碎股賣出、歷史曲線與庫存一致。流水儲存依鍵去重，
重匯不會重複記流水。細節與 snippet 全在票 04。

## 拍板紀錄（2026-08-04，四題四答）

1. 顯示格式：**原值去尾零（最多 6 位）**；固定 5 位小數案否決。
2. 被略過交易的去重鍵：**維持現狀（確認即記鍵）＋一次性修復**；「略過不記鍵」案否決。
3. 手動賣出容差：**一併加**（滿賣判定＋超賣擋板，公式不動）。
4. 台股整數防呆：**此輪不做**。

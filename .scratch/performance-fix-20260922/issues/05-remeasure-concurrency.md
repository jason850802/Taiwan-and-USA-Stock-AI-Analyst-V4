# 05 — 重量排程並決定是否需要調整上限

Status: ready-for-agent
Blocked by: 04
Type: task

本檔為正式票據。依本案共同驗收手冊執行。

## 要交付的結果

在本機環境與名稱解耦已確定後，用十／三十檔資料分離剩餘 queue 等待；形成可重跑的「維持三槽」或「需另行調整」結論，不先假設提高上限。

## 實作範圍

- 先量現有三槽的十／三十檔首檔、全部完成、等待、總請求數、實際 HTTP 峰值、名稱補齊與匯率完成。
- 只有剩餘排隊明顯時，才以假上游比較 3／4／6 槽，涵蓋正常延遲、429 與錯誤；候選數字只作實驗。
- 維持跨重疊刷新共用上限、同 key 合併、已啟動工作占槽到真正完成、匯率優先、移除取消與名稱流量納入上限。
- 若三槽已達整體目標，保留三槽並以量測結案；其他候選有穩定收益時，先提交比較與需要改動的測試契約再決定後續。

## 驗收條件

- [ ] 十／三十檔三槽基準完整，能拆出 runtime、名稱與排程影響。
- [ ] 有比較候選時，每組皆保存請求總數、峰值、等待、首檔／全部與錯誤數，且負載與 cache 條件一致。
- [ ] 價格改善不靠取消、漏項、背景無界併發或跳過匯率／名稱工作。
- [ ] 少量真行情只驗證選定候選，不用它宣稱長期不會 429。
- [ ] 得出可重跑的維持或調整結論；若調整仍待使用者／契約決策，保留 OPEN，不讓 07 宣稱全案完成。

## 邊界

既有測試因候選上限變更而紅時，按專案規則視為語意訊號，不直接改期望值。

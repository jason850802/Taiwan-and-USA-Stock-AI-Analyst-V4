### 安全姿態：第 2、11、12 條為什麼不修

這三條看起來是攻擊面，實際上是**同一件已被 Phase 4 明確接受的設計**的不同切面：

- **共享密鑰本來就是公開的**——`VITE_PROXY_SECRET` 是 build-time 注入前端 bundle，
  任何人打開 JS 就讀得到。當時的原話是「提高門檻、非密碼學保證」
  （見 `.planning/phases/04-hardening/04-RESEARCH.md` 的共享密鑰段）。
- **行情端點的 CDN 快取本來就繞過整個 guard**——`s-maxage=60, stale-while-revalidate=300`，
  60～360 秒視窗內根本不進 `applyGuards`，當時列為 T-B1-01 accept。
- 因此「來源雙缺放行」「限流身分可偽造」「fail-open 遮蔽超限判定」都不改變實質暴露面：
  能繞的人本來就繞得過，收緊這三處只是把門檻從很低調成稍高。

**真正的成本天花板是 GCP 的 Gemini 每日配額**，那是手動設在 Google Cloud console、
不在 git 裡的東西（`04-RESEARCH.md` 列為手動步驟）。**repo 內找不到它被確認完成的紀錄**——
這件事的重要性高於上面 13 條加總，但屬於雲端帳號操作，未在本輪處理。

## Grill 期預埋（2026-07-28，逐檔通讀發現）

1. **Gemini 請求驗證對 temperature 與 thinkingConfig 不驗型別直接透傳。**
   現行後果：字串 temperature 會原樣進 SDK config，由上游報錯，最後被分類成
   UPSTREAM_ERROR 而非 BAD_REQUEST，使用者看到的文案會指錯方向。
   建議：裁決是否在驗證器補型別檢查（補了就是行為變更，另開票）。

2. **來源檢查在 origin 與 referer 雙缺時放行**（curl／server-to-server 不帶
   header 即通過來源這一關）。
   現行後果：這類請求的實際防線只剩 shared secret＋限流；PROXY_SHARED_SECRET
   未設的部署，等於對無 header 請求開放（僅限流兜底）。
   建議：裁決是否維持現狀（放行是既有設計，避免鎖死健康檢查類請求），
   或在 secret 未設時收緊雙缺放行。

3. **Gemini 錯誤分類用 `\b5\d{2}\b` 對「訊息文字」比對 5xx**，中文訊息含
   「500」字樣（如字數限制文案）也會命中。
   現行後果：無實害——命中與否結局都是 UPSTREAM_ERROR，與 Yahoo 分類器
   既有的 L-1 前瞻性佔位註記同型。
   建議：純紀錄，不動。

4. **LLM_PROVIDER 設無效值時丟出的錯誤掛在 MISSING_KEY 這個 code 下**，
   語意上是設定錯誤而非缺金鑰。
   現行後果：前端把它當缺金鑰類文案顯示；訊息本身有寫清楚支援值，堪用。
   建議：純紀錄；日後前端要對 code 做分流再議。

## 票 01（config）2026-07-28

5. **設定值打錯時一律靜默降級，沒有任何啟動期檢查。** 兩個已上鎖的實例：
   (a) 模型名設成只有空白的字串（`GEMINI_MODEL_FAST='   '`）——空白是 truthy，
   `||` 攔不住，會原樣當型號送去上游，錯誤要到 SDK 回 404 才浮現，使用者看到的是
   「模型無法使用」而非「設定打錯」；
   (b) 允許來源多打一條斜線（`https://a.example//`）——去尾斜線只去一層，留下的
   `https://a.example/` 永遠比不中任何 Origin header（瀏覽器送的 Origin 不帶尾斜線）。
   該白名單項不是全死：來源檢查的 referer 那一路仍可能命中（Referer 剛好是站台根頁時
   字串相等），但實務上等於「只有從根頁發出的請求過得了」，其餘一律被擋，
   而部署方以為自己設好了整個網域。
   現行後果：兩者都不會有紅字或徵兆，只會在使用時以「像是別的問題」的形式出現。
   建議：裁決要不要加一道啟動期設定值檢查（trim 後為空即報錯、尾斜線全部去掉）。
   這是行為變更，要修另開票。

6. **PROXY_SHARED_SECRET 設成空字串等同完全停用驗證**（與未設同路），
   且**與第 2 條疊加**：來源檢查對「origin 與 referer 雙缺」的請求放行，
   secret 又被空值停用時，不帶 header 的請求（curl／server-to-server）就只剩限流擋得住。
   現行後果：Vercel 環境變數貼上失敗、或 `PROXY_SHARED_SECRET=` 這種寫法，
   都會讓這道驗證無聲關閉——部署方以為開著。
   建議：與第 2 條一起裁決（同一個攻擊面）。可能的收法是「secret 設定存在但為空 → 啟動期報錯」。

## 票 02（finmind）2026-07-28

7. **日期驗證只驗形狀不驗曆法**：`9999-99-99` 通過樣式檢查、原樣送往 FinMind。
   現行後果：上游回空資料或錯誤，使用者看到「查無資料／上游錯誤」而非「日期打錯」，
   除錯方向被誤導。
   建議：裁決是否加真實曆法檢查（行為變更，另開票）。

8. **cacheSecondsForDataset 收任意字串、不擋白名單外值。**
   現行後果：現行唯一呼叫鏈都先過 validateFinMindParams，無實害；但簽名層級沒有
   型別防護，未來繞過驗證的新呼叫點會拿到「未知 dataset 靜默走短快取」且零徵兆。
   建議：純紀錄；要收緊簽名（`AllowedDataset`）屬另票的型別權衡。

9. **兩個錯誤分類器（finmind 與 gemini/http）都對字串型 status 做 `Number()` 隱式轉型**
   （`{status:'429'}` 與 `{status:429}` 判定相同）。
   現行後果：多一層韌性，無實害；但轉型是隱式且無註解，日後改判定邏輯的人
   未必知道字串 status 也在射程內。兩檔測試已各自把這行為鎖住。
   建議：純紀錄，不動。

## 票 03（yahoo）2026-07-28

10. **interval／range 大小寫敏感，與 symbol 的大小寫寬容不一致**：symbol 小寫會被
    自動大寫化救回，`1D`／`10Y` 卻直接 BAD_REQUEST。
    現行後果：同型錯誤（大小寫打錯）在不同參數上寬鬆度不一，除錯時容易誤判方向；
    現行前端固定送小寫故無實害。
    建議：裁決是否讓 interval／range 比照 symbol 正規化（行為變更，另開票）。

## 票 05（ratelimit）2026-07-28

11. **限流計數對象完全信任用戶端可自帶的 header**（x-forwarded-for／x-real-ip 都是
    請求方可偽造的；含補充：x-forwarded-for 空字串與未設等價，會繼續往下層找）。
    現行後果：夾帶假 header 即可換限流身分、重置額度，等同繞過限流。主防線本來就是
    shared secret＋來源檢查，限流是兜底——但這個可偽造性應記成「已知取捨」而非疏漏。
    另注意 Vercel 平台會覆寫 x-forwarded-for，實際暴露面取決於部署環境是否可信任該覆寫。
    建議：裁決「維持現狀純紀錄」或「只信平台注入來源」（行為變更，另開票）。

12. **fail-open 讓「限流服務出錯」與「未超限」在回傳上不可分**：任一 limiter 丟錯，
    `Promise.all` 整體 reject，其餘 limiter 本來的「超限」判定也一併被放行蓋過。
    現行後果：純可觀測性缺口（只有 console.warn 一行），非行為錯誤。
    建議：純紀錄；要加 metric／分級 log 另開票。

## 票 06（guard）2026-07-28

13. **「來源不合法」與「shared secret 不合法」兩種 403 共用 code `BAD_REQUEST`**，
    只有 message 文字不同（「請求來源不被允許。」vs「請求未通過驗證。」）。
    現行後果：只看 code 的呼叫端（前端文案分流、監控告警）無法區分兩種失敗，
    要分只能比對 message——但 message 是給人看的文案，不是穩定介面。
    建議：裁決是否給兩者獨立 code（如 BAD_ORIGIN／BAD_SECRET；行為變更，另開票）。

# Findings — api/_lib 首批行為鎖（裁決區）

> 行為鎖過程翻出的可疑行為集中在這裡。「要不要修」由使用者裁決，要修另開票；
> 首批測試一律照現行行為鎖，不動產線碼。
> 每條寫：現象／現行後果／建議。實作票發現新的往下 append（標上票號）。

## Grill 期預埋（2026-07-28，逐檔通讀發現）

1. **Gemini 請求驗證對 temperature 與 thinkingConfig 不驗型別直接透傳。**
   現行後果：字串 temperature 會原樣進 SDK config，由上游報錯，最後被分類成
   UPSTREAM_ERROR 而非 BAD_REQUEST，使用者看到的文案會指錯方向。
   建議：裁決是否在驗證器補型別檢查（補了就是行為變更，另開票）。

2. **來源檢查在 origin 與 referer 雙缺時放行**（curl／server-to-server 不帶
   header 即通過來源這一關）。
   現行後果：這類請求的實際防線只剩 shared secret＋限流；PROXY_SHARED_SECRET
   未設的部署，等於對無 header 請求開放（僅限流兜底）。
   建議：裁決是否維持現狀（放行是既有設計，避免鎖死健康檢查類請求），
   或在 secret 未設時收緊雙缺放行。

3. **Gemini 錯誤分類用 `\b5\d{2}\b` 對「訊息文字」比對 5xx**，中文訊息含
   「500」字樣（如字數限制文案）也會命中。
   現行後果：無實害——命中與否結局都是 UPSTREAM_ERROR，與 Yahoo 分類器
   既有的 L-1 前瞻性佔位註記同型。
   建議：純紀錄，不動。

4. **LLM_PROVIDER 設無效值時丟出的錯誤掛在 MISSING_KEY 這個 code 下**，
   語意上是設定錯誤而非缺金鑰。
   現行後果：前端把它當缺金鑰類文案顯示；訊息本身有寫清楚支援值，堪用。
   建議：純紀錄；日後前端要對 code 做分流再議。

## 票 01（config）2026-07-28

5. **設定值打錯時一律靜默降級，沒有任何啟動期檢查。** 兩個已上鎖的實例：
   (a) 模型名設成只有空白的字串（`GEMINI_MODEL_FAST='   '`）——空白是 truthy，
   `||` 攔不住，會原樣當型號送去上游，錯誤要到 SDK 回 404 才浮現，使用者看到的是
   「模型無法使用」而非「設定打錯」；
   (b) 允許來源多打一條斜線（`https://a.example//`）——去尾斜線只去一層，留下的
   `https://a.example/` 永遠比不中任何 Origin header（瀏覽器送的 Origin 不帶尾斜線）。
   該白名單項不是全死：來源檢查的 referer 那一路仍可能命中（Referer 剛好是站台根頁時
   字串相等），但實務上等於「只有從根頁發出的請求過得了」，其餘一律被擋，
   而部署方以為自己設好了整個網域。
   現行後果：兩者都不會有紅字或徵兆，只會在使用時以「像是別的問題」的形式出現。
   建議：裁決要不要加一道啟動期設定值檢查（trim 後為空即報錯、尾斜線全部去掉）。
   這是行為變更，要修另開票。

6. **PROXY_SHARED_SECRET 設成空字串等同完全停用驗證**（與未設同路），
   且**與第 2 條疊加**：來源檢查對「origin 與 referer 雙缺」的請求放行，
   secret 又被空值停用時，不帶 header 的請求（curl／server-to-server）就只剩限流擋得住。
   現行後果：Vercel 環境變數貼上失敗、或 `PROXY_SHARED_SECRET=` 這種寫法，
   都會讓這道驗證無聲關閉——部署方以為開著。
   建議：與第 2 條一起裁決（同一個攻擊面）。可能的收法是「secret 設定存在但為空 → 啟動期報錯」。

# 05 — 多檔庫存讀取有整體併發上限

Status: resolved — 2026-09-21
Blocked by: 04
Type: task

本檔為正式票據。依主 PLAN 的共同驗收手冊執行。

## 要交付的結果

大量庫存逐檔完成更新，連續按刷新也不造成無上限請求尖峰；一檔失敗不阻塞其餘股票。

## 實作範圍

- 先測 1、10、30 檔的請求峰值、首檔與全部完成時間，再以現有併發工具為基礎控制排程。
- 工程起始上限為同一庫存載入範圍最多 3 個實際報價請求，包含所需匯率。重疊的手動／自動刷新共用控制範圍，不是每次啟動各自 3 條 worker。
- 快取命中即時顯示，不必排隊等網路；失敗釋放槽位；匯率不得排在一長串股票之後餓死。
- 一般重複讀取沿用現有共用請求。force 仍表示要求新資料；可合併尚未開始的舊排隊意圖，但最後一次 force 必須真正完成，不能只讀舊快取。
- 取消或取代排隊工作時，完整結束其 loading／等待者狀態；已移除持股不再啟動，進行中結果遵守 04 的身分守衛。

## 驗收條件

- [x] 30 檔一般載入與重疊兩次刷新，量得範圍內實際網路峰值均 ≤ 3，不以 worker 數自報代替量測。
- [x] 快取命中的持股立即顯示；匯率最晚在首批排程取得機會；單檔失敗其餘仍完成。
- [x] 最後一次刷新得到新資料，沒有永久 loading、無限重複請求或隊列堆積。
- [x] 同時有重複代碼、移除持股、卸載及失敗重試時，併發與清理行為仍正確。
- [x] 前後列出峰值、總請求數、首檔及全部完成時間，誠實說明限制併發對全量時間的影響。
- [x] 假資料瀏覽器 30 檔情境通過；型別檢查、相關行為測試與完整 gate 通過。
- [x] 獨立 code-review：Standards、Spec 均已處置，證據與提交完成。

## 邊界

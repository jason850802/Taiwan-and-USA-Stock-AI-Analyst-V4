# 01 — 庫存健檢改走串流（含邊生成邊顯示）

Status: ready-for-agent
Blocked by: 無（與票 02 平行）

## 目標

把**健檢分析函式**接到專案裡**已經在生產環境跑的串流路徑**，取得 180 秒上限，
消滅「同一檔按健檢時好時壞」；單檔健檢順帶做到**邊生成邊顯示**，
使用者約 4 秒就看到報告開始長出來。

## 規格依據

spec.md 全文（含實測數據與兩道閘門的餘裕證明）。

## 背景（讀碼前先知道）

- 現況：健檢走**非串流**端點，後端等待上限 100 秒，逾時即砍。實測單檔要
  **104.7 秒**、三檔 **125.4 秒**——連單檔都超過，所以偶爾成功才是例外。
- 串流路徑**已在線**：市場分析頁的 AI 分析就是用它跑的，前端客戶端、後端端點、
  守門與限流、測試全都到位。健檢只是沒接上。
- **現成的分流形狀**：進場分析那支函式已經是「帶 `onChunk` 走串流、不帶走非串流」
  的三元式，照抄即可，不要發明新形狀。

## 範圍

做（健檢分析函式，服務層）：
- 加**選用**參數 `onChunk`，以現成三元式分流到串流客戶端／非串流客戶端。
- **payload 一個位元組不變**：prompt、system instruction、mode、temperature、
  thinkingConfig 全部照舊。既有呼叫端不改也必須能編譯。

做（健檢 hook）：
- **單檔** handler：傳入把累積文字寫進該檔 `fullResult` 的 callback，
  期間狀態維持 `loading`。（串流客戶端給的是**累積全文**不是增量，直接覆寫即可。）
- **批次** handler（全部健檢／重試失敗共用）：一樣走串流以取得 180 秒上限，
  但 `onChunk` **不做 per-symbol 寫回**（理由見紅線 2）。

做（庫存頁）：
- 結果視窗的載入態分兩種：
  - `loading` 且 `fullResult` **非空** → **渲染部分報告**（沿用既有的 Markdown 呈現），
    配一個小轉圈或「產生中」標示，讓使用者知道還沒寫完。
  - `loading` 且 `fullResult` **為空** → 維持現行的「分析中…」。
- 「重新健檢」在 `loading` 期間仍為 disabled（現況不變）。

不做：
- **提示詞與 system instruction 的任何字元變動**（受 snapshot 逐位元組鎖定）。
- 調整任何逾時常數（見驗收最後一項——碰逾時是語意決策，要回報數字給使用者拍板）。
- 持股表、健檢徽章、決策解析、切段 fallback 階梯、併發上限、世代守衛結構。
- 批次的逐檔進度顯示。
- 報價快取三票（`.scratch/quote-cache-and-health-retry/`）的任何檔案。
- 元件測試（專案慣例不寫）。

## 紅線

1. **世代守衛必須涵蓋部分結果的寫回。** 單檔與批次共用一個 per-symbol 單調遞增
   計數器，保證「重疊飛行時較早起跑者不得覆蓋較晚起跑者」。串流會讓**每一次
   partial 都是一次寫回**——若 partial 不比對世代，舊的那趟會在新的那趟跑到一半時
   把畫面蓋掉。**每次 partial 寫回都要過守衛，比照最終結果的寫回。**
2. **批次的切段仍吃完整文本。** per-symbol 切段要求每個代碼都認領到段落，
   部分文本切不開；批次的 `onChunk` 不得拿去做 per-symbol 寫回。
3. **「全部健檢」與「重試失敗」的 LLM 呼叫數仍是 1**（不得因改串流而變成逐檔呼叫）。
4. **既有測試零修改。** 服務層是 additive（選用參數）、提示詞零變動。
   既有測試紅燈＝語意變更的訊號，**停下來問使用者，不准改期望值**。

## 驗收

**自動化**
- [ ] 服務層新增案例（照既有那支帶 `onChunk` 的測試形狀）：
  - [ ] 帶 `onChunk` → 打串流端點；不帶 → 打非串流端點（分流的機械證明）。
  - [ ] **兩條路送出的 prompt 與 system instruction 逐字相同**（改路不改內容的證明）。
- [ ] `npm run gate` 全綠（既有 snapshot 不得變動）。

**DOM／實機實測**（起 dev 環境用 `start-dev` skill）

- [ ] **不再擲骰子**：對同一檔**連按兩次健檢，兩次都成功**。
      （這是本票存在的理由——現況是第二次幾乎必失敗。）
- [ ] **邊生成邊顯示**：按下健檢後開啟結果視窗，**10 秒內**畫面上已出現報告文字
      （不是「分析中…」），且文字持續增加直到完成。
- [ ] **完成態正確**：跑完後視窗顯示完整報告、該檔徽章更新為決策文字。
- [ ] **重新健檢同樣行為**：對已成功的檔按「重新健檢」，視窗不關、就地開始長字、
      跑完換成新報告。
- [ ] **批次未壞**：「全部健檢」跑完，每檔都拿到自己的段落（不是所有檔顯示同一份
      全文），且 Network 面板中 AI 請求為 **1 筆**。
- [ ] **重試失敗（N）未壞**：同上，1 筆請求、只有目標檔位更新。
- [ ] **快取仍有效**：收盤後（提示詞穩定時）對同一檔連按兩次重新健檢，
      第二次應**幾乎瞬間**完成（命中當日快取）。
- [ ] 全程 console 零紅字。
- [ ] **【回報，不要自己改】** 對**使用者的真實庫存**跑一次「全部健檢」，
      用碼錶記下實際耗時並寫進本票 Comments。若超過 **150 秒**，
      在票面明確標示「逼近 180 秒上限」並**回報使用者決定是否調高串流逾時**——
      **實作方不得自行調整任何逾時常數**。
- [ ] 收尾 `code-review`（雙軸 Standards＋Spec），merge 帶 `Code-Review:` trailer。

## 給接手方的提示

- 串流客戶端已經自己處理 AI 快取的讀寫，你不需要多做什麼；快取命中時
  **不會**有任何 `onChunk` 呼叫，會直接回完整文字——UI 要能接受「從空白直接跳完成」。
- 部分結果是 Markdown 的**未完成片段**，渲染時可能出現半個表格或沒收尾的清單，
  那是正常的，不要為此加緩衝或延遲顯示（那會抵消掉這張票的價值）。
- 實測數據（供對照）：單檔首字 4.0 秒／總 104.7 秒；三檔首字 4.1 秒／總 125.4 秒。
  若你量到的數字與這差很多，先懷疑環境或提示詞被改動，回報再繼續。

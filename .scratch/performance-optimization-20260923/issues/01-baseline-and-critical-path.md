# 01 — 固定目前基線並拆出主要等待

Status: ready-for-agent
Blocked by: 無
Type: task

## 要回答的問題

目前每支報價約四秒，時間究竟落在本機 dispatch、Yahoo cookie／crumb／chart、FinMind、queue 還是 UI？哪個可控段最值得先修？

## 工作

- 讀 PLAN、spec、acceptance 與現況稽核；核 HEAD／index／隱藏變更／缺檔／服務，保存來源。保留已完成的產品修正。
- 凍結 B1、B0、C 定義與新目標。舊 E0 失敗獨立列為不可量，不把取得 E0 warm 當本輪產品實作的前置。
- 沿用舊 raw 重播能力，只補入口前與 server fetch 的 trace 邊界；先固定上游、後小批真行情，分清 trace 與正式量測。
- 同來源比較目前入口、直連／proxy、固定上游的空回應與 GET；確認 Yahoo 模組實例及握手是否跨 HTTP 保留。
- 產出可對帳的單支請求與十檔臨界路徑、provider 預算表、三至五個可否證假設及排序。只選有證據的一個主要候選進入下一票。

## 驗收

- [ ] 一個可無人執行的命令能在目前路徑判紅，不只檢查程式沒拋錯；附保存 trace 與退出碼。
- [ ] queue／TTFB／body／發布、handler 前後及 cookie／crumb／chart 各段有數字；跨程序時鐘不直接相減。
- [ ] 實際環境一致、來源及 PID 可核對，沒有秘密值／雜湊。
- [ ] 有明確決定：本機長駐分支值得驗證，或以數據否證並轉到已定位的上游／前端段。
- [ ] 第一票以一個完整 session 為界；沒有無限新增工具代數。若缺關鍵邊界，精確列阻斷而非宣稱已找到根因。
- [ ] 檢查本票工具的判紅能力、獨立覆核與精確提交；狀態／交接完整。

## 停手

已有兩次相同 E0 失敗，不原樣重跑；沒有新機制證據不得加長 timeout。若需要碰金融語意、真帳本或真 AI，停止該分支。完成後只交辦下一票，不連做產品原型。

# Spec：庫存備份與回灌（P1）

Status: ready-for-agent
建立：2026-07-27（to-spec，承 grill-with-docs）
依據：`docs/adr/0001-portfolio-backup-restore-overwrite.md`、詞彙表 `CONTEXT.md`

> 詞彙一律照 `CONTEXT.md`：**備份**（不叫匯出）、**回灌**（不叫匯入／還原）、
> **本體資料**、**可重建資料**、**預備份**。「匯入」一詞已被對帳單功能佔用，不得混用。

## Problem Statement

使用者的全部庫存資料只活在單一瀏覽器的 localStorage：769 筆真實交易、目前持股、
已實現損益帳本、配息推算結果與各種手動修正。清瀏覽器資料、換電腦、或瀏覽器 profile
損毀，這些資料即滅失，而且**重建不回來**——對帳單原檔就算還在，也救不回配息推算
結果、手動調整與賣出紀錄。App 至今沒有任何把資料帶出去的路徑；想看全貌只能開
DevTools 敲 Console。使用者等於把數年的交易紀錄押在一個沒有副本的瀏覽器上。

## Solution

庫存頁提供一顆「備份」按鈕，把**五把本體 key** 收進單一 JSON 檔下載到使用者電腦；
另一顆「回灌」按鈕吃這個檔，**整包覆蓋**現有的五把本體 key，讓使用者回到備份當下
的狀態。回灌前會顯示筆數對照的確認框，並在按下確認的當下**自動先下載一份現況的
預備份**，讓回錯檔也救得回來。回灌完成後整頁重新載入，畫面即為備份內容。

這不是雲端同步：檔案在使用者自己的電腦上，換機自己帶。

## User Stories

1. 作為一個把數年交易紀錄放在瀏覽器裡的投資人，我想要一鍵把全部庫存資料存成一個檔案，好讓我在清瀏覽器資料前有副本。
2. 作為一個要換電腦的使用者，我想要把備份檔帶到新機器上回灌，好讓我不必重新匯入所有對帳單。
3. 作為一個怕手滑的使用者，我想在回灌前看到「現有 N 筆 → 換成 M 筆」的對照，好讓我確認自己選對了檔案。
4. 作為一個回錯檔的使用者，我想要系統在覆蓋前自動幫我留一份現況，好讓我能立刻回灌回去。
5. 作為一個備份檔存了很久的使用者，我想要檔案裡有匯出時間，好讓我在多個備份檔之間分辨新舊。
6. 作為一個使用者，我想要備份檔名自帶日期時間，好讓我不必打開檔案就能排序。
7. 作為一個好奇的使用者，我想要備份檔是人看得懂的 JSON，好讓我能自己檢查裡面有什麼。
8. 作為一個使用者，我想要備份包含目前持股，好讓回灌後庫存表跟備份當下一樣。
9. 作為一個使用者，我想要備份包含完整交易流水，好讓回灌後歷史損益曲線能重新回推。
10. 作為一個使用者，我想要備份包含已實現損益帳本，好讓回灌後我的已實現數字不會歸零。
11. 作為一個使用者，我想要備份包含每日快照，好讓回灌後曲線的既有點位不必重算。
12. 作為一個使用者，我想要備份包含對帳單匯入紀錄（去重鍵），好讓回灌後重新匯入同一份對帳單不會重複計算。
13. 作為一個使用者，我不想要備份包含收盤價快取，好讓備份檔保持精簡——那是抓得回來的東西。
14. 作為一個使用者，我不想要備份包含 AI 分析快取，好讓備份檔不塞當日即棄的內容。
15. 作為一個使用者，我想要在回灌一個不是本 App 產生的檔案時被明確擋下，好讓我的現有資料不被亂七八糟的內容蓋掉。
16. 作為一個使用者，我想要在回灌一個未來版本的備份檔時被擋下並看到原因，好讓我知道要去更新 App 而不是以為資料壞了。
17. 作為一個使用者，我想要在備份檔驗證失敗時，現有資料**一個位元組都不變**，好讓失敗的回灌不會造成任何損害。
18. 作為一個使用者，我想要回灌是全有全無的，好讓不會出現「寫到一半失敗」留下半殘資料的狀態。
19. 作為一個使用者，我想要回灌完成後畫面自動反映新資料，好讓我不必自己按重新整理才知道成功了。
20. 作為一個第一次使用的空庫存使用者，我想要在回灌時不要被下載一個空的預備份檔，好讓我的下載資料夾不被垃圾檔塞滿。
21. 作為一個使用者，我想要備份與回灌的按鈕就在庫存頁我平常操作的地方，好讓我不必去翻設定選單。
22. 作為一個使用者，我想要備份按鈕在庫存是空的時候仍然可用（或明確禁用），好讓我不會對著沒反應的按鈕困惑。
23. 作為一個使用者，我想要回灌的確認框把「這個動作會捨棄備份之後新增的資料」講清楚，好讓我知道自己在放棄什麼。
24. 作為一個使用者，我想要在選檔後、確認前就看到檔案的匯出時間與筆數，好讓我在按下去之前就發現選錯檔。
25. 作為一個使用者，我想要取消回灌時什麼都不發生（連預備份都不下載），好讓取消是真的取消。
26. 作為一個使用者，我想要在 localStorage 空間不足導致回灌寫入失敗時看到明確訊息，好讓我知道該去清空間而不是以為資料消失了。
27. 作為未來的維護者，我想要備份的 key 清單集中在一處，好讓之後新增第六把 key 時只改一個地方。
28. 作為未來的維護者，我想要備份模組不認得領域型別，好讓某個 store 的 decode 收緊時不會讓既有資料悄悄漏出備份。

## Implementation Decisions

### 模組與接縫

- 新增**單一純模組**負責備份與回灌的全部邏輯，**Storage 由呼叫端注入**（比照
  `utils/persistentStore.ts` 的 `storage?: Storage` 作法），模組頂層不得觸碰
  `localStorage`（沿用專案純模組守則，Node 測試環境可安全 import）。
- 該模組**刻意不認得領域型別**（不 import `PortfolioItem`／`StoredTxn` 等）。
  它只認 key 名字，搬的是每把 key 的**原始 JSON 值**。理由：備份必須存
  「現場實際有什麼」而不是「現行 decode() 肯收什麼」——否則未來版本或任何被
  decode 拒收的資料會悄悄不進備份，這對保命功能是不可接受的洞。
- 對外介面（四件事，命名由實作決定）：收集備份、驗證備份檔、套用備份、
  計算筆數（供確認框對照用；筆數統計不得因為某把 key 形狀怪異而拋錯）。

### 備份範圍

- 五把**本體資料** key：持股、交易流水、匯入紀錄、已實現帳本、每日快照。
  清單集中定義在備份模組內，是這個功能唯一的 key 來源。
- 排除**可重建資料**：收盤價快取、AI 分析快取（含所有 `gemini_cache_v1|` 前綴條目）。
- 缺席的 key（例如全新使用者還沒有已實現帳本）在備份檔中以「不存在」表示，
  回灌時該 key 應被移除而非寫入空值——回灌後的 storage 必須與備份當下等價。

### 備份檔格式

- 單一 JSON 物件，自帶 **schema 版本**與**匯出時間**（ISO 8601），資料段是
  「key → 該 key 的值」的對應。值以解析後的 JSON 存放（不是字串轉義），
  讓檔案人類可讀、可 diff。
- 位元組保真由往返測試證明：五把 key 的現行寫入全部經由 `JSON.stringify`
  （persistentStore 工廠），故 parse→stringify 往返後位元組相同。
- 檔名帶日期時間，可直接排序。

### 回灌流程與防護

- **驗證先於寫入，全有全無**：先驗完整份備份檔（是本 App 的檔、schema 版本認得、
  資料段形狀合法），任一項不過即整包拒收，**現有資料一個位元組不動**、不寫任何 key。
  未知 schema 版本的處理沿用 `txnStore` 的既有慣例（拒收並 warn，原資料保留）。
- **確認框**顯示筆數對照：現有的持股／交易／已實現筆數 → 備份檔的對應筆數，
  並標明備份檔的匯出時間，文案須明講「備份之後新增的資料會被捨棄」。
- **預備份**：使用者按下確認的當下，先以現況產生一份備份並下載，然後才覆蓋。
  現況五把 key 全部缺席（全新使用者）則跳過，不下載空檔。
- 取消時不得有任何副作用（不下載預備份、不寫任何 key）。
- 寫入失敗（quota）須回報明確訊息；不得靜默。
- **回灌成功後整頁重新載入**。理由：五把 key 中只有兩把在 App.tsx 有 React state
  鏡像，其餘三把是呼叫點直接讀寫；重新載入讓所有狀態在 mount 時重讀，
  「回灌後 storage 裡就是備份檔」成為結構保證而非要靠斷言去守的性質。
  也避免每日快照 hook 在回灌後立刻寫一筆當日 live 快照蓋掉剛回灌的內容。

### UI

- 兩顆按鈕放在庫存頁既有的工具列，與「匯入對帳單」同一排。
- 選檔沿用專案既有的隱藏 `<input type="file">` ＋ 按鈕觸發模式（對帳單匯入已在用）。
- 下載用瀏覽器原生 `Blob` ＋ object URL（**禁裝新套件**是專案紅線），用完釋放 URL。
- 確認框沿用專案既有的 Modal 元件與樣式，不另造。

## Testing Decisions

**什麼是好測試**：只測外部行為——「給定 storage 的某個狀態，備份出來的內容是什麼」
「給定一個備份檔，回灌後 storage 變成什麼」。不測模組內部怎麼迭代 key、不斷言私有
函式。所有斷言都落在 storage 的可觀察內容或函式回傳值上。

**受測模組**：備份模組（唯一接縫）。UI 層（按鈕、確認框、選檔、下載、reload）
不寫測試——與現況一致（21 支測試全在 `utils/`，專案零元件測試），
且該層是薄膠水，沒有可獨立驗證的邏輯。

**必含案例**：

1. **往返鐵則**：塞入五把 key 的真實形狀 fixture → 備份 → 清空 storage → 回灌 →
   五把 key **逐位元組相同**。這是本功能的核心驗收，紅了就是保命失效。
2. 可重建資料不進備份：storage 裡有收盤價快取與 AI 分析快取時，備份檔不得含它們。
3. 缺席 key 的往返：某把 key 不存在時備份與回灌後仍不存在（不得長出空值）。
4. 拒收非本 App 的檔案：現有資料不變、不寫任何 key。
5. 拒收未來 schema 版本：現有資料不變、不寫任何 key。
6. 拒收資料段形狀非法的檔案（如資料段不是物件）：現有資料不變。
7. 全有全無：驗證失敗時**一把 key 都沒被碰過**（用會記錄寫入次數的 storage stub 斷言）。
8. 筆數統計：對五把 key 的真實 fixture 回報正確筆數；某把 key 形狀怪異時不拋錯。
9. quota 失敗回報：storage 寫入拋錯時回傳失敗而非靜默。
10. 備份檔含 schema 版本與匯出時間欄位。

**Prior art**（照抄既有寫法，不要另創風格）：

- `utils/persistentStore.test.ts` —— 記憶體 Storage stub（含 `failTimes` 模擬 quota）、
  「舊格式直接可讀」的 JSON 字面量 fixture、「寫出的位元組形狀」斷言。本 spec 的
  測試骨架直接沿用這一支的 stub 與斷言風格。
- `utils/importReplay.test.ts`／`utils/importPlan.test.ts` —— 對帳單匯入是本功能最近的
  類比：純函式承載全部邏輯、UI 只做膠水，測試全打在純函式上。
- `utils/geminiCache.test.ts` —— 同樣是「key 形狀與段位」的行為鎖，可參考其註解密度。

**驗收 gate**：專案機械 gate（`npm run gate`）全綠，既有測試零修改。
另需實機驗證一輪：起 preview、種入資料 → 備份下載 → 改動資料 → 回灌 →
確認筆數回到備份當下、console 零紅字。

## Out of Scope

- **合併式回灌**（把備份併進現有資料）。已實現帳本與每日快照沒有去重鍵，合併會把
  同一筆賣出的損益算兩次且 UI 無異常徵兆；需求場景（多台電腦各記一半）目前不存在。
- **部分回灌**（只回灌某幾把 key）。
- **CSV 報表**（P2，屆時另行 grill 決定欄位與編碼）。
- **「清空全部資料」功能**（獨立的毀滅性功能，需要自己的防護設計）。
- **雲端同步／自動備份／備份提醒**。
- 收盤價快取與 AI 分析快取的備份。
- 備份檔加密或密碼保護。
- 跨 App 版本的資料遷移（回灌只處理本 App 自己產生的、版本認得的備份檔）。

## Further Notes

- 覆蓋式的已知代價：備份之後新增的資料，回灌即捨棄。這是 ADR-0001 明知並接受的
  取捨，由預備份吸收風險。實作時**不要**自作主張加上合併邏輯來「幫使用者省事」。
- 回灌後歷史損益曲線的收盤價快取為空，第一次進曲線頁會重抓行情、稍慢幾秒，
  屬預期行為，不需額外處理（可在確認框文案順帶提一句）。
- 備份模組是唯一知道「哪些 key 屬於本體資料」的地方。日後新增第六把本體 key 時，
  改那份清單即可；漏改的後果是新資料不進備份，`CONTEXT.md` 的詞彙表應同步更新。
- 專案禁裝新 npm 套件；下載與選檔一律用瀏覽器原生 API。
